# ТЗ модуля `atomic_model.topology`

**Статус:** детализированная спецификация перед реализацией  
**Дата:** 2026-09-27  
**Связанные решения:** ADR-0090, ADR-0091, ADR-0092, ADR-0099, ADR-0101, ADR-0111

## 1. Роль модуля

`atomic_model.topology` создаёт неизменяемую геометрию одной симуляции и отвечает на вопросы «какие позиции существуют?», «какой это тип позиции?», «кто с кем контактирует?» и «может ли занятую конфигурацию связывать цепочка контактов с металлом?». Модуль не хранит атомы, не бросает RNG и не выбирает физические события.

После создания симуляции топология, область металла и поле перемещений не меняются. Изменяются только занятость позиций в `SimulationState` и положение уже существующих атомов.

## 2. Входная конфигурация

| Поле | 2D | 3D | Правило |
|---|---|---|---|
| Размерность | `2` | `3` | Обязательное поле; смешивать типы позиций разных размерностей нельзя. |
| Область металла | Ортогональный простой замкнутый контур по сетке | Прямоугольный параллелепипед | Контур/объём задаётся до первого реального акта. Произвольные неортогональные 2D-контуры — будущая версия. |
| Поле перемещений | Сетка вокруг области | Объёмная сетка вокруг области | Протяжённость по каждой оси — `3L`, где `L` — наибольшая сторона исходной области металла. |
| Направляющие 3D | Не применяется | Вкл./выкл. | Это только настройка отображения; не часть топологии и не меняет физику. |

Область металла должна быть связной. Нулевая площадь/объём, самопересекающийся 2D-контур и выход области за границы поля являются ошибками конфигурации.

## 3. Сущности и неизменяемые данные

### 3.1 Позиция

```text
SiteKey
  dimension: 2 | 3
  coordinates: tuple[number, ...]
  kind: lattice | interstitial
  metal_relation: interior | boundary | outside
```

- `lattice` — узловая позиция серой сетки.
- `interstitial` — позиция между узлами: центр ячейки в 2D или центр куба в 3D; в отображении ей не соответствует серый узел.
- `metal_relation` определяется только фиксированной областью металла, а не текущей занятостью.
- `interior` применяется к узловым и межузельным позициям геометрически внутри области металла; `boundary` — к узлам её фиксированной границы; вся позиция вне области имеет `outside`.

Координаты должны быть дискретными и однозначно сериализуемыми. Внутреннее представление не использует вычисления с плавающей точкой: допустимы целочисленные полуединицы (например, масштабирование координат в два раза).

### 3.2 Графы

| Граф | Назначение | Рёбра |
|---|---|---|
| `contact_graph` | Проверка физической связности занятой структуры | геометрическое соприкосновение позиций: узловые соседи и связь межузлия с окружающими узлами |
| `movement_graph` | Поиск допустимых локальных целей событий | только правила разрешённых переходов, включая осевые межузельные `hop` |
| `shortest_path_graph` | Проверка перехода во вторую оболочку | манхэттенские кратчайшие пути между исходной и целевой позицией |

Графы строятся из одного набора `SiteKey`, не зависят от занятости и хранятся в топологии. Любое ребро обязано ссылаться на существующие позиции.

### 3.3 Предварительно вычисляемая классификация

Модуль должен отдавать для каждой позиции:

- принадлежность области металла и её класс (`interior`, `boundary`, `outside`);
- тип позиции (`lattice`, `interstitial`);
- соседей по контакту;
- осевых межузельных соседей;
- манхэттенское расстояние до другой позиции;
- признак достижимости в пределах поля;
- расстояние до границы поля для UI-предупреждения.

## 4. Контракты запросов

Имена ниже являются контрактными; точный язык и классы реализации выбираются в коде.

| Запрос | Результат | Ошибки |
|---|---|---|
| `site_at(coordinates, kind)` | `SiteKey` либо отсутствие позиции | `PositionOutsideField` для координаты вне поля |
| `classify(site)` | тип позиции и отношение к металлу | `UnknownSite` |
| `contact_neighbors(site)` | существующие геометрические контакты | `UnknownSite` |
| `axial_interstitial_neighbors(site)` | 4 соседа в 2D / 6 в 3D для межузлия; пусто иначе | `UnknownSite` |
| `manhattan_distance(source, target)` | `r=Σ|Δcoord|` в физической сетке | `DimensionMismatch`, `UnknownSite` |
| `shell(source, r)` | позиции оболочки `r`; для модели допустимы только `r=1,2` | `UnsupportedShell` при другом `r` |
| `all_shortest_paths(source, target)` | все кратчайшие манхэттенские пути | `NoPath` или `UnknownSite` |
| `validate_occupancy(occupied)` | успех либо структурированный список нарушений | см. раздел 6 |

Сервис событий использует `shell` и `all_shortest_paths`, но сам модуль топологии не решает, является ли цель физическим событием и какой у неё вес.

## 5. Геометрические правила

### 5.1 Оболочки

Дистанция равна `r=|Δx|+|Δy|` в 2D и `r=|Δx|+|Δy|+|Δz|` в 3D. Запрос оболочки принимает только номера `1` и `2`. В 3D диагональные переходы узел↔межузлие с числовым расстоянием `r=1,5` принадлежат первой оболочке наряду с осевыми переходами `r=1`; вторая оболочка имеет `r=2`.

Для источника в узле в первую оболочку входят осевые узловые позиции и диагональные межузлия. Для источника в межузлии — осевые межузлия и диагональные узлы. Вторая оболочка строится тем же манхэттенским правилом и никогда не выходит за пределы поля.

`interstitial_interstitial` использует только осевых межузельных соседей: 4 в 2D и 6 в 3D. Диагональный межузельный переход одним актом отсутствует.

### 5.2 Связность занятых позиций

Вход `occupied` — двусторонне согласованный индекс «позиция → атом». Проверка выполняется так:

1. Проверить существование всех позиций и единственность занятости.
2. Взять занятые узлы области металла как источники связности.
3. Обойти `contact_graph` только через занятые позиции.
4. Для каждого занятого межузлия и каждой занятой внешней позиции потребовать достижимость от источника.

Таким образом, каждый внешний/межузельный атом имеет непрерывную цепочку соприкасающихся атомов до металла. Не разрешается создавать, перемещать или оставлять атом в изолированной компоненте.

### 5.3 Граница поля

Переход за границу поля всегда недопустим. Когда занятая позиция входит в заранее заданную зону предупреждения у границы, топология сообщает расстояние, а UI показывает предупреждение. Размер зоны предупреждения задаётся в конфигурации представления и не изменяет ни граф, ни физические вероятности.

## 6. Ошибки валидации

| Код | Условие | Сообщение пользователю |
|---|---|---|
| `INVALID_METAL_DOMAIN` | Пустая, несвязная или самопересекающаяся область | «Невозможно создать связную область металла.» |
| `POSITION_OUTSIDE_FIELD` | Координата вне фиксированного поля | «Позиция находится за границей поля перемещений.» |
| `UNKNOWN_SITE` | В состоянии указана несуществующая позиция | «Выбранная позиция отсутствует в этой симуляции.» |
| `SITE_OCCUPIED` | Попытка занять уже занятую позицию | «Эта позиция уже занята атомом.» |
| `DISCONNECTED_ATOM` | После действия атом не связан с металлом | «Атом нельзя оставить отдельно от решётки.» |
| `DIMENSION_MISMATCH` | Смешаны 2D- и 3D-позиции | «Позиция не соответствует размерности симуляции.» |

API преобразует эти коды в стандартизированную ошибку DTO; рендерер не воспроизводит проверки самостоятельно.

## 7. Выход для отображения

Топология передаёт в `RenderFrame` только неизменяемые данные, нужные для показа:

- контур/объём области металла;
- видимые границы поля;
- координаты занятых узлов и межузлий из состояния;
- класс позиции для назначения постоянного цвета;
- метку «близко к границе поля»;
- для 3D — данные Z-срезов, из которых UI отберёт непустые карточки.

Постоянный цвет вычисляется по отношению положения к металлу: любая внутренняя позиция — оранжевая, граничный узел — зелёный, позиция вне металла — красная. Поэтому внутренний межузельный атом остаётся оранжевым, а внешнее межузлие — красным. Жёлтый не передаётся как состояние: его вводит рендерер лишь на время анимации события.

## 9. Граница ответственности

- `initialization` выбирает, какие допустимые позиции занять в начальной конфигурации.
- `events` решает, какие из геометрически доступных кандидатов являются физически допустимыми, назначает им веса и выбирает ровно один исход.
- `simulation_management` делает команду атомарной, хранит историю и вызывает проверку топологии перед фиксацией snapshot.
- `api` не меняет топологию после старта и переводит доменные ошибки в DTO.
- `src` показывает данные `RenderFrame`, но не вычисляет физическую связность и не изменяет состояние напрямую.
