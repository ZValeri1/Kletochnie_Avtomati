# Стратегия тестирования Gamma Irradiation Application

## 1. Назначение документа

Документ определяет тестирование утверждённой модульной архитектуры. Тесты привязываются к новым публичным классам и контрактам, а не к текущему монолитному устройству проекта.

Старый тест удаляется только после появления и успешного прохождения заменяющего теста новой архитектуры. Golden Master не используется: ожидаемое поведение фиксируется явными входными данными, инвариантами и публичными DTO.

## 2. Распределение тестов

```text
70% — доменная логика
20% — API, интеграция и DTO-контракты
10% — браузерные E2E
```

Целевое branch coverage:

| Область | Покрытие |
|---|---:|
| Атомная модель | 85–90% |
| Управление симуляциями | 75–85% |
| Хранение и API | 70–80% |
| Frontend-компоненты | 60–70% |
| Общий проект | 70–80% |

Покрытие является индикатором. Приоритет имеют критические сценарии и инварианты, а не достижение процента любой ценой.

Порядок проверок:

1. Unit-тесты доменной логики.
2. Интеграционные тесты API.
3. Контрактные тесты DTO.
4. Короткие E2E smoke tests.
5. Длительные симуляционные и нагрузочные тесты отдельно.

## 3. Общие правила тестирования

- Для воспроизводимых сценариев используются фиксированные seeds.
- Для проверки конкретного события применяется принудительная энергия или контролируемый `RandomSource`.
- Тесты файлового хранения используют временный каталог.
- Общий `projects/` в тестах не используется.
- Доменная логика тестируется без React и FastAPI.
- Физическая корректность не проверяется только screenshot-тестами.
- Перед commit нового состояния проверяются инварианты.
- При ошибке проверяется сохранение последнего корректного snapshot.
- Тесты не должны зависеть от порядка их запуска.
- Каждый тест создаёт собственные модель, session и временные файлы.

## 4. Unit-тесты атомной модели

### 4.1 `Topology`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Создание 2D-топологии | `(4,3)` | 12 lattice-позиций, корректное число interstitial и bridge |
| Создание 3D-топологии | `(3,4,5)` | 60 lattice-позиций, hollow-позиции на гранях |
| Минимальный размер | `(2,2)` и `(2,2,2)` | топология создаётся без висячих ссылок |
| Недопустимый размер | одна ось или значение меньше 2 | контролируемая ошибка валидации |
| Соседство | любая внутренняя позиция | все соседи существуют; обратная связь присутствует |
| Supports | bridge/hollow site | только существующие lattice-позиции |
| Детерминированность | два вызова с одинаковыми размерами | эквивалентные sites и связи |

### 4.2 `SimulationState`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Идеальное состояние | валидная топология | один атом на каждом lattice site |
| Дублирование позиции | два atom ID на одном site | ошибка инварианта |
| Несуществующая позиция | atom с неизвестным site key | ошибка инварианта |
| Несогласованный occupancy | atoms и occupied различаются | ошибка инварианта |
| Рабочая копия | исходное состояние | изменение копии не изменяет исходное состояние |

### 4.3 `EventEngine`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Событие ниже порога | atom, энергия ниже всех доступных порогов | `NoChange` или только неактивные диагностические outcomes |
| Событие на пороге | atom, энергия равна порогу | событие становится активным |
| Нормировка | atom с несколькими событиями | сумма активных вероятностей равна 1 |
| Нулевые веса | доступные события с нулевыми весами | определённое fallback-поведение без NaN |
| Направление | симметричные назначения относительно X | направление `+X` имеет больший коэффициент |
| Занятая позиция | candidate destination занята | candidate отсутствует |
| Диагностический вызов | state, atom, energy | state и RNG не изменяются |

### 4.4 `EventExecutor`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Shift | atom и свободная lattice vacancy | атом перемещён, occupancy согласован |
| Swap | два соседних атома | позиции атомов обменены |
| Frenkel | lattice atom и interstitial destination | одна lattice vacancy и один interstitial atom |
| Recombine | interstitial atom и vacancy | vacancy заполнена, interstitial устранён |
| Surface transition | surface atom и допустимое назначение | корректное новое состояние атома |
| Недействительный candidate | занятое/несуществующее назначение | ошибка, исходное состояние не изменено |
| Сохранение атомов | любое штатное событие | число атомов до и после одинаково |

### 4.5 `MetricsCalculator`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Идеальная решётка | все атомы на lattice | 0 vacancies, 0 defects, entropy 0 |
| Пара Френкеля | одна vacancy и один interstitial | vacancies 1, interstitials 1, defects 2 |
| Surface defect | одна vacancy и один surface atom | surface defects 1, корректное общее число defects |
| Доза | total dose и число атомов | `dose_ev_per_atom = total_dose / atom_count` |
| Чистота функции | один state, два вызова | одинаковый результат; state не изменён |

### 4.6 `SimulationEngine`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Создание состояния | config и seed | валидные InitialStateResult и metrics |
| Успешный шаг | валидный state и RNG | новый state, event, metrics; исходный state не изменён |
| No change | forced energy 0 | событие `no_change`, физическое состояние прежнее |
| Ошибка инварианта | executor возвращает невалидный state | StepResult не фиксируется; возвращается доменная ошибка |
| Probabilities | atom и energy | нормированный список без изменения state/RNG |

## 5. Property-based тест критических инвариантов

Для генерации использовать Hypothesis.

| Генерируемые данные | Проверяемое свойство |
|---|---|
| 2D/3D размеры | все позиции и связи валидны |
| энергия 0–Qmax | вероятности конечны и неотрицательны |
| начальные дефекты | атомы и occupancy остаются согласованными |
| последовательность шагов | количество атомов сохраняется |

После каждого сгенерированного шага проверяется:

```text
atom_count_before == atom_count_after
len(occupied) == atom_count
occupied atom IDs уникальны
atom positions уникальны
все позиции существуют
metrics не содержат NaN или Infinity
```

## 6. Unit-тесты управления симуляциями

### 6.1 `SimulationSession` и `SimulationHistory`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Commit | StepResult с ожидаемой revision | state и revision обновлены атомарно |
| Конфликт revision | устаревшая expected revision | ошибка конфликта; state не изменён |
| Ошибка шага | SimulationError | сохранён last valid snapshot, статус `FAILED` или `PAUSED` по контракту |
| Изоляция | две session с разными state | изменение первой не меняет вторую |
| Undo | state0 → state1 → undo | восстановлены state0 и RNG0 |
| Redo | undo → redo | восстановлены state1 и RNG1 |
| Ветвление | undo → новый step | старая redo-ветка удалена |

### 6.2 `SimulationManager` и `SimulationScheduler`

Эти классы проверяются совместно, чтобы не повторять одинаковые сценарии на двух уровнях.

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Create | валидный config | уникальный simulation ID и статус `CREATED`/`PAUSED` |
| Create batch | count N и master seed | N независимых sessions с воспроизводимыми derived seeds |
| Run | paused session | статус `RUNNING`, задачи поступают Scheduler |
| Pause | running session | новые задачи не создаются; текущая завершается; статус `PAUSED` |
| Stop | одна из нескольких sessions | остановлена только выбранная session |
| Invalid command | step для завершённой/неизвестной session | структурированная ошибка |
| Failure isolation | engine error в session A | session B продолжает работу |
| Последовательность одной session | несколько команд одного ID | выполнение строго FIFO, без одновременных команд |
| Параллельность | команды разных simulation IDs | выполнение перекрывается во времени до заданного лимита |
| Лимит | задач больше `max_parallel_simulations` | одновременно работает не больше установленного числа |
| Timeout | зависшая вычислительная команда | timeout error; Scheduler принимает следующие задачи |
| Эквивалентность | A/B/C параллельно и последовательно | при одинаковых seeds результаты каждой симуляции совпадают |

### 6.3 `SnapshotFactory` и `EventHub`

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Валидная session | полное внутреннее состояние | DTO со schema version, ID, revision, atoms и metrics |
| Mutable state | изменение state после создания DTO | ранее созданный DTO не изменяется |
| Ошибка session | failed session | публичный status и структурированная ошибка без внутренних объектов |
| Подписка | client подписан на simulation A | получает только события A |
| Порядок | события revisions 1,2,3 | клиент получает их в этом порядке |
| Отключение | закрытый WebSocket | client удаляется, публикация продолжается |

## 7. Интеграционные тесты данных и исследований

Проверяются целые операции, а не отдельные функции сериализации и статистические утилиты. Все файловые операции выполняются во временном каталоге.

### 7.1 Сохранение и загрузка

| Вход | Ожидаемый выход |
|---|---|
| Две симуляции со state, RNG, history, events и metrics | после save/load обе симуляции полностью восстановлены, данные не смешаны |
| Повреждённый или неподдерживаемый формат | структурированная ошибка, частично восстановленный проект не создаётся |
| Существующий проект и `overwrite=false` | ошибка, существующий проект не изменён |
| Существующий проект и `overwrite=true` | проект полностью заменён без старых файлов |
| Искусственный отказ записи | старый проект остаётся читаемым, временные файлы не публикуются |

### 7.2 Эксперимент и статистика

| Вход | Ожидаемый выход |
|---|---|
| Несколько завершённых симуляций с известными рядами и bootstrap seed | корректный и воспроизводимый `AggregateResult` с mean, min, max, percentiles и confidence interval |
| Одна failed simulation среди успешных | успешные результаты сохранены, ошибка отражена в результате серии |
| Отмена running experiment | новые шаги не ставятся, статус серии `CANCELLED` |

### 7.3 Экспорт

| Вход | Ожидаемый выход |
|---|---|
| Несколько simulation IDs и согласованные revisions | отдельный каталог каждой simulation, manifest и aggregate result |
| Экспорт работающей симуляции | зафиксирована выбранная revision, выполнение симуляции продолжается |
| Ошибка экспорта | итоговый каталог не публикуется частично |

## 8. Интеграционные тесты API

| Тест | HTTP/WebSocket вход | Ожидаемый выход |
|---|---|---|
| Основной цикл | create → step → get snapshot | 201 при создании; после шага новые event, revision и snapshot |
| Неверная конфигурация | размеры меньше 2, отрицательный порог | 422 и структурированный `ApplicationError` |
| Конфликт revision | step со старой expected revision | 409; состояние не изменено |
| Жизненный цикл | run → pause → resume → stop | корректные переходы статусов |
| Save/load | сохранить, удалить из registry, загрузить | восстановлены state, RNG, history и metrics |
| Несколько моделей | создать A и B, выполнить шаг A | snapshot B не изменён |
| WebSocket | подписка на A | snapshot/events только A в правильном порядке |

## 9. Контрактные тесты DTO

Backend и frontend должны использовать одинаковые JSON fixtures или JSON Schema.

Обязательны три общих fixtures:

1. `SimulationSnapshot` вместе с `SimulationMetrics`.
2. `SimulationEvent`.
3. `ApplicationError`.

| Вход | Ожидаемый выход |
|---|---|
| Валидный JSON fixture | Python и TypeScript успешно декодируют одинаковые данные |
| Нет обязательного поля | оба клиента отклоняют сообщение |
| Неизвестная `schema_version` | оба клиента возвращают ошибку версии |
| Дополнительное необязательное поле | принимается согласно политике совместимости |
| Неверный тип или координата | сообщение отклонено |

## 10. Frontend unit-тесты

| Тест | Вход | Ожидаемый выход |
|---|---|---|
| Валидный 2D snapshot | atoms с координатами `[x,y]` | валидный 2D `RenderFrame` |
| Валидный 3D snapshot | atoms с `[x,y,z]` | валидный 3D `RenderFrame` |
| Повреждённый snapshot | отсутствует обязательное поле | возвращается ошибка, используется last valid snapshot |
| Snapshot A | сообщение для simulation A | изменяется только state A |
| Устаревшая revision | revision меньше или равна текущей | store не откатывается назад |
| Ошибка 3D renderer | искусственное исключение | Error Boundary показывает fallback; controls работают |

## 11. E2E smoke tests

E2E-набор должен оставаться небольшим.

| Сценарий | Входные действия | Ожидаемый результат |
|---|---|---|
| Основной 2D-путь | открыть приложение → создать 2D-модель → step | новая revision и метрики отображены |
| Основной 3D-путь | создать 3D-модель | snapshot получен, Three.js-сцена отображена |
| Параллельные модели | запустить A и B → pause A | A остановлена, B продолжает работу |
| Данные | save → load → export | ключевые параметры восстановлены, экспорт создан |

Скриншоты используются только как дополнительная проверка представления, но не как доказательство корректности физической модели.

## 12. Длительные тесты

Запускаются ночью или вручную.

| Сценарий | Вход | Ожидаемый выход |
|---|---|---|
| Устойчивость модели | одна simulation, разные размеры/seeds, 10 000+ шагов | инварианты сохраняются, память не растёт без ограничений |
| Параллельная нагрузка | 20–50 simulations, задач больше числа workers | состояния не смешиваются, лимит Scheduler соблюдается, очередь завершается |
| Массовый эксперимент | множество runs, bootstrap и экспорт | расчёт завершается, результат воспроизводим, экспорт валиден |

После получения baseline фиксируются допустимые среднее и p95 времени шага, память на simulation и время save/load/export.

## 13. Порядок внедрения тестов

1. Определить публичный интерфейс нового класса или DTO.
2. Написать тест ожидаемого поведения новой архитектуры.
3. Реализовать класс до прохождения теста.
4. Перевести следующий сценарий со старой реализации на новую.
5. Удалить старый тест только после успешной замены.
6. После появления Manager/Scheduler добавить concurrency tests.
7. После разделения frontend добавить mapper/store/renderer isolation tests.
8. Удалить старый код после прохождения полного нового набора.

### 13.1 Режимы запуска во время реорганизации

```shell
# Полный быстрый backend-набор
python -m pytest

# Только unit-тесты
python -m pytest tests/unit

# Frontend mapper/store/DTO и четыре E2E-сценария
cd apps/frontend
pnpm test:architecture
```

Каталоги `tests/unit`, `tests/property`, `tests/integration` и `tests/contract`
входят в основной быстрый запуск. Длительные проверки из `tests/long` оставлены
отдельными и не входят в обязательную проверку.

## 14. CI и Git-процесс

### 14.1 На каждый commit

```text
Domain unit tests
Property-based test: 50–100 примеров
Session/history tests
Data tests во временном каталоге
API tests основного цикла и ошибок
DTO contract tests
Frontend mapper/store tests
```

Целевое время: до 1–2 минут.

### 14.2 На Pull Request

```text
Весь быстрый набор
Concurrency tests
Frontend production build
4 Playwright smoke scenarios
```

Целевое время: до 5 минут.

### 14.3 Ночью или вручную

```text
Property-based test: 1000+ примеров
10 000+ шагов
20–50 параллельных simulations
Memory/performance profiling
Массовый эксперимент и экспорт
```

```text
feature-ветка
    ↓
быстрые unit + integration + contract tests
    ↓
Pull Request
    ↓
concurrency + build + 4 E2E smoke tests
    ↓
main — рабочая версия
```

## 15. Критерии готовности набора

- Проверяются 2D- и 3D-топологии.
- Проверяются основные группы атомных переходов.
- Проверяется нормировка вероятностей.
- Проверяются критические инварианты состояния.
- Проверяются seed и восстановление RNG через undo/redo.
- Проверяются изоляция и параллельность симуляций.
- Проверяется отказ одной симуляции без остановки остальных.
- Проверяется полный save/load round trip во временном каталоге.
- Проверяются DTO между Python и TypeScript.
- Проверяется сохранение `last_valid_snapshot` при ошибке.
- Выполняются четыре E2E-сценария.
- Общий coverage находится в диапазоне 70–80%, атомная модель — не ниже 85% branch coverage.
